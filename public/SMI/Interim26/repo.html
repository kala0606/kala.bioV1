03

AGENTS.md

Codex reads AGENTS.md before it works in your folder. Use it to tell Codex who it's working for, what it must never do, and how your project is built.

AGENTS.md
# Working on this project

## Who this is for

This is a student project in a generative art studio. The student writes as an
authored identity, [identity name], who [one line: position and condition].
Read identity.md and manifesto.md before suggesting anything creative.

## Authorship rules

- Propose; don't decide. Explain options and wait for the student to choose.
- Never write or rewrite manifesto.md, final-statement.md, log.md or the
  "I rejected, and why" lines in authorship.md. You may question them.
- Ask for a plan to be agreed before writing code. Then work one step at a time.
- Explain every change in plain language, as if to an artist new to code.
- Don't use AI image generation in the system.
- If you're unsure a library, dataset or reference exists, say so.

## How the code is built

- Language and setup: [e.g. JavaScript with p5.js / Python with ...]
- Every parameter lives in config/params.json, with a default and a range.
- All randomness comes from one seeded generator. Same seed and params, same output.
- Outputs are saved to outputs/digital/ as NNN_seed-SEED_[key params].svg (or .png).
- Keep the code small enough for the student to read and explain.

## Don't touch

- data/ (raw data is read, never modified)
- outputs/ (never delete outputs)
- docs/photos/

## Run

[the command to run the system]
[the command to render a batch of seeds]

Fill in the brackets on Day 1 with what you know, and update it as the identity and the system settle. A short, true AGENTS.md is better than a long, generic one.

04

Git habits

Git is your undo button and your record. Four habits cover the month.

  1. Commit before you ask Codex for a change.

    Then you can always return to a version that worked.

    git add -A git commit -m "before: line weight from deficit"
  2. Commit after every step that works.

    Small commits are easier to read and to undo.

  3. Say what changed, not that something changed.

    "line weight follows deficit" tells a story; "update" doesn't. Log entries use log: day 07.

  4. Push at the end of every day.

    Your laptop is not a backup. Pushing also lets the facilitator see the work.

    git push
Large filesGitHub refuses single files over 100 MB and warns above 50 MB. Keep raw scans, videos and large meshes out of the repository: put them in .gitignore and store them on the studio drive, then link to them from the README.
05

.gitignore

Start with this and add to it.

.gitignore
# system files
.DS_Store
Thumbs.db

# dependencies and caches
node_modules/
__pycache__/
.venv/

# secrets: never commit these
.env
*.key

# large files: store on the studio drive instead
*.mov
*.mp4
*.zip
raw/

If you ever commit a password or key by mistake, tell the facilitator straight away. Deleting the file doesn't remove it from the history.

06

Going public

From Day 17 the repository is linked from the exhibition, so anyone can read it.

  • Read it as a stranger would. Open the README on your phone. Does it make sense without you there?
  • Check for anything private. Personal data, other people's photos without permission, keys or passwords.
  • Credit your sources. Data in data/SOURCES.md, references in references.md, code you adapted in the README.
